# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

`meta-fetch` (crate `github-repo-meta-fetch`) is a Rust CLI that incrementally syncs a GitHub repo's issues and pull requests into a local SQLite cache, then projects that cache into a **deterministic Markdown tree** for offline AI-agent review. The Markdown output is pure derived data — safe to commit to git.

Three subcommands (`src/cli.rs`): `sync` (fetch + render), `render` (re-project from cache, no network), `status` (watermarks, phases, counts).

## Commands

Prefer the `justfile` recipes:

- `just test` — full suite (`cargo test`). Run a single test: `cargo test <name>` (e.g. `cargo test maps_basic_fields`).
- `just lint` — `cargo clippy --all-targets --all-features -- -D warnings`.
- `just fmt` — **nightly** rustfmt; `.rustfmt.toml` uses nightly-only options. Always use `cargo +nightly fmt`.
- `just update-schema` — refresh the vendored `github-schema.json` via `graphql-client introspect-schema` (run only when a query needs a newly-added GitHub field).

CI (`.github/workflows/ci.yml`) runs fmt (nightly, `--check`), clippy, test, and an MSRV gate at **1.96.0** — keep new code compiling on that toolchain.

### Lint policy (enforced, see `~/.claude/rules/rust.md`)

- `[workspace.lints]` in `Cargo.toml` denies clippy `pedantic` and `unwrap_used` (warn). `#[allow(...)]` is **forbidden** — fix the lint, or suppress with a narrowly-scoped, deliberate `#[expect(...)]`. The crate-wide test exception for `unwrap_used` lives in `src/lib.rs` (`cfg_attr(test, …)`); integration tests under `tests/` opt in with `#![allow(clippy::unwrap_used)]` at the top.

## Snapshot tests

Render output is covered by `insta` snapshots (`src/render/snapshots/*.snap`). When intentional output changes break them, review with `cargo insta review` (or `cargo insta accept`). `*.pending-snap` files are gitignored. `tests/determinism.rs` asserts byte-identical re-renders.

## Architecture

Pipeline, top to bottom: **CLI → sync → github → store → render**, with **ratelimit** cross-cutting the network phases.

- **`github/`** — `GithubClient` wraps `octocrab` but uses its semi-internal `_post` so the raw HTTP response (and `X-RateLimit-*` headers) survives; the built-in `Octocrab::graphql` discards them, and the whole rate-limit subsystem depends on those headers. GraphQL types are generated by `graphql_client` from `.graphql` files in `github/queries/` against the vendored schema; `gql.rs` declares one `GraphQLQuery` struct per query. `auth.rs` resolves a token from `$GITHUB_TOKEN` then `gh auth token`. Taxonomy is the exception to GraphQL: `rest.rs` fetches labels/milestones via REST **conditional GET**, persisting per-resource ETags in the store — a 304 leaves the cached rows untouched.

- **`sync/`** — `Syncer::run` drives taxonomy (labels, milestones) then per-entity phases (issues, PRs); `--only` scopes a run to one entity phase. Each phase paginates `UPDATED_AT DESC` and **early-stops** when an item's `updatedAt` drops below the stored watermark. Each item (plus its drained comment/timeline/review pages) is persisted in its own transaction; the page cursor is checkpointed after every page; the watermark advances only on clean completion. `--full` walks everything and reconciles deletions (soft-delete via `mark_deleted_except`) — but **only on a fresh full run**, never a resumed one (a resumed run has an incomplete seen-set). Issues and PRs share comment/timeline mapping code via the `CommentNode`/`TimelineItem` traits. Issue **relationships** (parent, sub-issues, blocked-by, blocking) ride the issues phase: fetched inline on the issues page with overflow drained by dedicated pages, unified via the `RelNode` trait (`sync/relationships.rs`, mirroring `CommentNode`), and persisted as `issue_relationships` edges. Design spec: `docs/superpowers/specs/2026-07-02-issue-relationships-design.md`.

- **`ratelimit/`** — `budget` parses headers into buckets; `estimator` keeps an EWMA per query type (floored by a conservative per-type ceiling) to predict the next call's cost; `store` is a **shared, per-token** SQLite DB (keyed by a SHA-256 token `fingerprint`, see `fingerprint.rs`) so concurrent processes sharing one token can't both slip past the reserve floor — reservations use `BEGIN IMMEDIATE`. The `budget_ok` closure threaded into each sync phase reconciles the store from post-call headers, feeds the estimator, and atomically reserves against the floor. On hitting the floor: `--no-wait` pauses (checkpoint saved, exits **75** / `EX_TEMPFAIL`, resumable); otherwise it sleeps until reset (capped by `--max-wait`).

- **`store/`** — SQLite via `rusqlite` (bundled) with `rusqlite_migration`; migrations are `include_str!`'d SQL in `store/migrations/` and applied on `open()`. Schema is node-id-keyed with soft-delete (`deleted` column) and a single-row `repo_meta`. The `Executor` trait abstracts over `Connection`/`Transaction` and **deliberately omits** `transaction()`, so any `&impl Executor` fn is statically incapable of opening a nested transaction.

- **`render/`** — `render_tree` is a pure projection: per-issue/PR Markdown files (zero-padded by `repo_meta.padding_width`, which only grows), each with YAML frontmatter (incl. relationship keys), plus cross-cutting `by-label`/`by-milestone`/`by-state` index tables, `labels.md`/`milestones.md`, and `hierarchy.md` — a parent/sub-issue tree capped at depth 8 (GitHub's nesting limit), with cross-repo targets rendered as plain text marked `— external`. Derived index dirs are wiped and rebuilt; stale per-entity `.md` files (soft-deleted items) are pruned. No network — drives the `render` subcommand and the tail of `sync`.

- **`paths.rs`** — `etcetera` XDG strategy. Repo DBs live at `{data_dir}/github-repo-meta-fetch/{owner}/{repo}.sqlite3`; the shared rate-limit DB at `{state_dir}/.../rate-limits.sqlite3` (native AppData on Windows).
